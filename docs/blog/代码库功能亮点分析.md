# Thinker Agent Scope 代码库功能亮点分析



---

## 一、一句话定位

**这不是一个"会聊天的 Agent Demo"，而是一套把 LLM 关进笼子里的企业运维查询编排平台。**

它的核心命题不是"让模型更聪明"，而是 **在模型不可信的前提下，如何保证业务查询的正确性、完整性与可审计性**。全库 5.4 万行源码中，真正花在"防御 LLM"上的工程量占比极高——这是它区别于普通 Agent 项目的本质特征。

## 三、三层架构：解耦做得很干净

```
┌─ LLM 编排层 ──────────────────────────────────────────┐
│  语义路由(hybrid) · 能力边界 · 复合问句 · 执行协调        │
│  → 决定"何时调工具 / 补参 / 追问 / 出图表"                │
└──────────────────────┬────────────────────────────────┘
┌─ 平台能力层（与 AgentScope 完全解耦）─────────────────┐
│  工具注册 · 依赖图 · 递归补参 · 候选项 · 失效传播        │
│  · 表单生成 · 约束快照 · 分析算子 · UI block 协议        │
└──────────────────────┬────────────────────────────────┘
┌─ runtime adapter ─────────────────────────────────────┐
│  AgentScope v2 → 统一流式事件（仅做映射，不承载状态机）   │
└───────────────────────────────────────────────────────┘
```

**关键契约**：平台能力层是**纯函数**，不 import tools、不发 HTTP。这条规则不是口头约定，而是**被测试固化**的——`test_analysis_engine.py::test_analysis_engine_has_no_tool_or_http_dependency` 直接读源码断言不含 `src.tools` / `httpx` / `requests`。

## 四、十二个功能亮点

### 1. 声明式工具工厂：一份 Pydantic 定义，三处消费

127 个工具**零注册代码**。`@api_tool` 装饰器 + 类属性声明 + 目录自扫描（`discover_api_tool_executors()` 递归 `__subclasses__()`），加一个文件就自动成为一个工具。

同一个 Pydantic Model 同时充当三个角色：

- **API 契约**（HTTP 请求/响应校验）
- **LLM tool schema**（给模型的参数定义）
- **表单 schema**（前端渲染依据）

参数侧另有一套声明式注解：

```python
Annotated[str, DependsOn(DeviceTypeProvider, default_params={...}),
          FormField(label="设备类型", control="select", order=1)]
```

**价值**：新增业务接口只写 Provider，平台层不动一行。这是"开闭原则"的教科书级落地。

---

### 2. 对 LLM 的权力收束：一切白名单化

这是全库最一致的设计哲学。模型在每个环节都被限制在**只能做选择题，不能做填空题**：

| 环节 | 模型能做什么 | 模型不能做什么 |
| --- | --- | --- |
| 表单展示 | 建议 label / placeholder / control / order | 新增字段、改 required、改依赖关系 |
| 参数决策 | 只看到 `options[].label` | 看不到 value，**禁止**自行列候选或调依赖工具 |
| 后续问题推荐 | 从 `allowed_candidates` 里选 id 排序 | 捏造字段值；不在候选内一律丢弃 |
| 聚合查询 | 声明式 `AggregationSpecV1` | 数据源必须显式声明 measures/dimensions |

展示 JSON 由 `ALLOWED_FIELD_DISPLAY_KEYS` 白名单校验，**任一错误则整体回滚**（`applied=False`），不做部分应用。

**价值**：把"LLM 幻觉"从概率问题变成了结构性不可能。

---

### 3. 服务端约束快照：把用户已确认条件变成不可篡改的不变量

`query_constraints.py` 为每次查询生成服务端快照，来源有严格优先级：

```
form_submit > intent_text > conversation_context > prefill_decision > default > model_tool_call
```

守卫 `QueryInvocationGuard.validate()` 提供**双向防护**：

- **防漏传**：模型少传高优先级字段 → `restored_fields` 自动回填
- **防篡改**：值不一致 → 记 `conflicts`，**禁止 HTTP 调用**，重新进入补参

配套 `ServerQueryConstraintStore.save_form()` 每次先 `clear()` 保证会话内唯一活跃表单，并用 `form_revision == server+1` 单调校验**阻止旧消息重放**。

**价值**：用户勾选的查询条件不会在后续多轮对话中被模型悄悄改掉。

---

### 4. 分层 fail-closed：四级逐级收窄的确定性拒答

不是"答不上来就硬答"，而是层层拦截：

```
① 能力边界层(capability_boundary) ── 零工具调用、亚秒级、纯文本
   └─ 9 个 MetricBoundary：维修时长 / 告警响应时长 / 天气关联 / 跨系统库存一致性
      / AI 异常准确率 / 重大能源异常 / AI 优化提效预估 / 告警责任归属 / 能耗预测
② 语义规划 terminal 态 ── 无可执行计划直接出未执行结论
③ 执行门控(tool_gating) ── 白名单外/未闭合约束/force_form 拦截
④ unsupported_intent_hints ── 规划期就 reject 越界意图（如"预测下月""根治"）
```

复合句含受支持业务词时会**放行正常链路**（`require_no_business_words` 保护），不会因一个不支持词误杀整句。

**价值**：把"不知道"变成一等公民能力，而不是失败态。

---

### 5. Hybrid 语义路由：性能与鲁棒性的精细平衡

`SEMANTIC_PLANNING_MODE=hybrid|llm|rules` 可切换，默认 hybrid：

- **规则快车道**：别名精确命中且置信度 ≥ `FAST_PATH_CONFIDENCE(0.9)` → 不调模型
- **LLM 规划**：`qwen3.6-flash`，`temperature=0`，`asyncio.wait_for` 超时 **3.0s**，预算 `PROMPT_BUDGET_CHARS=12000`
- **熔断**：连续失败 3 次冷却 300s，但熔断是**实例级**的，不阻断同进程其他会话
- **缓存**：600s / 256 条，但 `prior_query_context` 请求**跳过缓存读写**（避免跨会话串目标），且缓存命中后**仍重做覆盖校验**——注释明确写着"缓存不是协议边界"

**价值**：既有规则的确定性，又有 LLM 的泛化力，还能在模型故障时优雅降级。

---

### 6. 递归依赖求解 + 失效传播

`DependencyGraphBuilder` 从 `x-dependency` 递归展开 provider 的 `request_fields`，用 `visited` + `stack` 双集合 DFS，**命中 stack 即记"依赖图存在环"**并置 `has_cycle`（返回 error 而非崩溃）。

失效传播分两层：

- **运行时**：上游值变化后重查候选，`_value_in_options()` 不命中即 `_drop_fields()` 剔除并重新出表单
- **前端联动**：生成 `upstream_invalidation_rules`，且明确只认 provider request schema 中 required / 带 dependency 的字段为上游，**不把 selector 兄弟字段当上游**

候选查询缓存键 `dependency_cache_key = json([provider, provider_args], sort_keys=True)`；`authorization_failed` 抛 `DependencyOptionAuthorizationError` 并转成 `form_errors`，**不崩溃**。

---

### 7. 复合问句：部分失败绝不掩盖

一句"查 A 和 B"，若 B 不支持：

- `_drop_unsupported_plans()` 把被拒子句转成 **limitations** 挂到保留的 A 计划上
- `collect_execution_limitations` 合并 ≤8 条、每条截断 500 字
- `_emit_execution_limitations` 以 `content_delta` **确定性注入**"能力限制"段
- 模型版摘要额外标注 **"禁止表述为全部完成"**

**价值**：这是绝大多数 Agent 项目的通病——少查了一项却宣称"都查完了"。这里用机制而非提示词来杜绝。

---

### 8. 受限语义 UI Block 协议

```python
ChatMessageBlockType = Literal["chart","form","table","metric","report","suggestions"]
```

`ChartSpecV1` 是**受限语义**（`chartType ∈ {bar,line,area,pie,stacked_bar,gauge}` + dataset + xField/yFields），**拒绝下发原生 ECharts option**——防止模型注入任意图表配置。

`replace_block_id` 机制支持**同消息块状态迁移**：表单 → 生成中 → 结果就绪，前端按 `message_id + block_id` 替换而非无脑追加。

前端 `types/chat.ts` 用**可辨识联合**保证 `type` 与 `spec` 类型一一对应，编译期就能挡住类型错配。

---

### 9. 确定性分析算子：可重放、可解释、禁止因果

`analysis_engine.py` 三个纯函数算子：

- `group_share`：占比归一。全部 `tce>0` 按标煤折算才可跨量纲；单位混杂时 `comparable=False` 并声明"仅量级参考"
- `anomaly_flag`：两期波动判定。`AnomalyThresholds` **必须由调用方显式传** `change_ratio/min_sample`，**禁止内置魔法数**
- `evidence_join`：时序对齐归因。措辞上限"可能相关"，`method_note` 明示"不代表因果"

阈值与统计方法**随结果外显**并写入 `analysis_limitations`。

**价值**：AI 分析结论的每一步都可解释、可审计、可复现，且不越界下因果结论——这是企业场景的硬要求。

---

### 10. 全链路可观测性与事实闭环

- **workflow_trace**：单行 JSON 结构化日志，ContextVar trace_id，`_sanitize` 对敏感词置 `***`、正文转 `sha256+chars`，`AGENT_TRACE_ENABLED` 总开关
- **stream_events**：`agent_stream_events` 逐事件落 PG（BIGSERIAL 保序），**支持会话完整重放**
- **numeric_provenance**：对终稿做数值与年月日**双审计**（1% 相对容差、万/亿换算、1e11 时间戳阈值排除、列表序号遮蔽），违例追加提示并留痕
- **model_evidence**：`render_model_evidence` 去敏（剔除 `*Id/_ids` 内部主键）+ 字符预算截断

---

### 11. 失败可恢复性设计贯穿全栈

| 层 | 失败处理 |
| --- | --- |
| 工具层 | 401 / 超时 / 无效参数**不抛出异常**，返回可重试提示（有测试固化） |
| WebSocket | 持久化失败**不抹掉已生成的响应、不终止连接**；客户端断连不阻断业务收尾 |
| 制品存储 | tmp + replace **原子写** + sha256 校验 + 会话级授权（内存/共享卷/S3+Redis 三实现） |
| 月报 | 缺数据指标显示 **"暂未接入"**，不阻断生成、不伪造数值，并提升到终态摘要 |
| 会话 | 软删除 `status=deleted` + `deleted_at`，部分索引 `WHERE deleted_at IS NULL` |

月报的 `_unavailable_value(status)` 区分五种状态：`暂未接入 / 暂无数据 / 数据获取失败 / 配置异常 / 范围未匹配`。

---

### 12. 权限下推到 SQL，而非应用层

- 非 `is_super_admin` **强制追加** `platform_user_id = requester.user_id` 到 WHERE 子句
- `get_conversation_owner()` 校验归属，WS 层 `_conversation_owner_error()` 先拦截
- 已绑定真实用户 ID 的会话**只能由同一用户继续**；后续 token 用户 ID 不一致或无 token → **直接拒绝回复**，不先落库覆盖 owner

**价值**：越权查询在数据库层就被挡住，不依赖应用代码的记忆力和自觉性。

## 五、附带亮点（值得一提）

- **实时语音输入**：`WS /ws/asr-input`，浏览器 AudioWorklet 采 PCM → dashscope `TranslationRecognizerRealtime` 桥接，跨线程 `run_coroutine_threadsafe` 回调，协议层强制 start→audio→stop 顺序
- **部门月报实时生成**：12 个章节 builder 并发 `asyncio.gather` → reportlab A4 + 中文字体渲染 PDF；服务器不存 PDF，点击下载时按原参数**实时重新生成**（内容以点击时数据为准）
- **智能表格布局**：`buildResponsiveTableLayout()` 按列名正则判定日期/数值/名称列自适应
- **聚合能力声明式**：`AggregationQueryService.validate_spec` 要求数据源显式声明 measures/dimensions，模型不能凭空聚合

## 六、可改进建议（客观）

1. **巨型文件待拆分**：`parameter_resolution.py`(6135)、`result_visualization.py`(5273)、`semantic_planner.py`(4673) 三个文件合计 1.6 万行，占源码 30%。建议按职责纵向拆分（如 visualization 的 61 个 `table` + 10 个 `chart` builder 可按业务域拆到 providers）。
2. **前端 `blockRenderers.tsx` 1444 行**偏大，且工具分派是 `tool_name` 硬编码 switch，可考虑注册表化。
3. **测试未在 CI 中可复现验证**：当前环境缺 `agentscope` 等依赖，`pytest` 无法运行。1,203 个用例的通过率需在 CI 中持续保障（`.gitlab-ci.yml` 已存在，建议确认其执行测试阶段）。
4. **文档与实现同步**：`README.md`(41KB) + `AGENTS.md`(36KB) 非常详尽，但也意味着维护成本高，建议定期校验文档中的机制描述是否与代码漂移。

## 七、总结

这个代码库最值得学习的地方**不是某个具体功能**，而是一以贯之的工程价值观：

> **把不确定性关进确定性的笼子里。**

LLM 负责它擅长的（理解意图、组织语言、排序选择），平台负责它必须负责的（正确性、完整性、可审计性、权限）。两者之间用**白名单、约束快照、类型契约、测试断言**划出清晰边界——而不是靠提示词恳求模型"请不要编造"。

在 127 个业务工具的规模下仍能保持这套纪律，是这个项目真正的亮点。
